# v0.2.0 开发规格：需求到测试用例主流程重构

**Status:** ready-for-agent

## Problem Statement

当前版本已经具备需求资料、来源追踪、需求评审、测试设计、测试用例、模型配置、AI 运行审计、模板和导出等后端能力，但用户工作台把资产来源、模型配置、AI 审计、需求导入、原子需求、冲突、测试维度、风险、自动化、模板、用例评审、任务发布、执行批次、治理指标、变更影响和报告连续铺在同一页面。普通测试工程师必须理解平台内部数据模型，才能完成最基本的需求分析和用例生成。

需求表、原子需求候选、测试项和验收条件存在重复或并列展示。用户无法在一个统一视图中判断“哪些需求将进入后续测试设计”。当前真实模型的需求分析一次生成过大的 JSON，容易超时、截断或发生结构校验失败；测试用例生成虽然创建了 AI 运行，但候选用例主要来自固定模板，模型输出没有真正驱动可执行的用例内容。因此，平台具备较多模块，却没有形成稳定、清晰、可交付的主流程。

计划参考的两个外部 Skill 提供了有价值的测试分析知识，但不能直接作为产品运行依赖。需求分析 Skill 以 00～08 共九个 Markdown 文件作为工作状态，适合 Agent 离线分析，不适合普通用户页面；用例生成 Skill 默认按八种测试方法分别生成文件和报告，并且与当前平台在 ID、优先级、用例字段和数据来源方面存在契约差异。原样接入会再次放大页面复杂度和运行不稳定性。

## Solution

把产品收敛为一条可中断、可恢复、可回退的纵向主流程：

> 上传需求文件 → 解析文档 → 结构预览 → 需求确认 → 评审建议 → 选择测试范围 → 生成测试用例 → 导出测试用例

项目工作台使用五个一级页签：上传文档、结构预览、新增建议、审核、测试用例。左侧保留模型服务配置、连接测试、当前运行进度、预计剩余时间、停止生成和步骤状态；资产来源、AI 运行审计、执行批次、治理指标、变更影响和详细报告继续作为后台能力或次级入口，不阻塞主流程，也不占据首屏。

结构预览页只提供一张按模块分组的需求确认表。每一行代表用户可以理解和选择的一条需求；验收条件、来源引用、分析说明和内部原子拆分作为行内摘要或展开详情。未勾选需求不进入评审、测试范围和用例生成。需求确认后由确定性逻辑分配稳定需求 ID。

两个外部 Skill 先派生为仓库内的两个项目专用 Agent Skill，分别命名为 `ai-test-design-requirement-analysis` 和 `ai-test-design-case-generation`。它们是 v0.2.0 测试分析工作流的规范来源，而不只是方法参考。后端工作流适配器按 Skill 定义执行步骤、组织模型输入、校验输出并保存阶段产物；前端负责把阶段产物可视化，并提供确认、筛选、停止、续跑和导出。浏览器不直接读取或执行 `SKILL.md`，外部模型服务也不需要理解 Codex Skill 格式。

需求分析专用 Skill 保留 Step 00～08 的完整业务语义：输入与版本基线、功能识别、业务规则、正常场景、异常场景、边界条件、隐性风险、测试点汇总和覆盖自检。产品以结构化阶段产物保存这些结果，并可按需导出 Skill 兼容的 Markdown，不要求用户直接管理九个文件。Step 08 完成后，将 Step 07 的测试点交给用例生成专用 Skill；后者负责测试方法选择、详细用例、用例编号、去重和质量检查。现有平台继续负责用例编辑、纳入或移除、稳定追踪、模板导出和后续回归资产管理。

系统只新增一个高层测试缝：以“已确认需求和所选测试范围”为输入，以“可编辑、可追溯的候选用例集”为输出的测试设计工作流。内部允许分成需求分析、建议生成、测试点规划和用例生成阶段，但这些阶段共享同一运行状态、进度、取消、重试和回退协议。

### v0.2.0 发布目标

- 恢复一条普通测试工程师能够独立完成的需求到用例主流程，而不是继续增加平行治理模块。
- 采用第二次旧版本的五页签信息架构，吸收第一次旧版本的模型配置、连接测试、进度、预计时间、停止、回退、导航、导出和步骤状态体验。
- 继续使用当前版本已经实现的来源追踪、文档解析、稳定 ID、模型适配、AI 运行、模板映射、用例模型和导出能力，避免重建平行后端。
- 通过两个仓库专用 Agent Skill 固化需求分析和用例生成方法，但保持 Agent Skill、运行时 Prompt 和产品领域模型三者边界清楚。
- 让真实模型输出真正参与需求分析与用例生成，同时以结构化校验、有限重试、停止恢复和模板回退保证流程可用。

### 页面与数据流程

| 页签 | 主要输入 | 用户主要操作 | 正式输出 | 解锁条件 |
|---|---|---|---|---|
| 上传文档 | 项目上下文、模型配置、需求文件 | 测试连接、上传、选择当前任务文件、启动解析 | 需求资料版本及解析结果 | 项目已创建 |
| 结构预览 | Step 00～02：材料基线、功能树、业务规则和语义需求 | 查看结构、筛选、勾选、展开规则与验收条件、确认需求 | 带稳定需求 ID 的已确认需求集合 | 至少一份文件可解析 |
| 新增建议 | Step 03～06：正常、异常、边界和风险分析 | 采纳、拒绝、修改、待外部确认 | 已处置分析建议及补充需求候选 | 需求确认完成 |
| 审核 | Step 07～08：测试点汇总、权限方向和覆盖自检 | 查看追溯关系、选择测试范围、处理盲区、确认交接 | 已确认测试项与测试点集合 | 阻塞建议已处理 |
| 测试用例 | 用例生成 Skill：已确认测试点、业务规则、模型或回退结果、用例模板 | 生成、停止、重试、编辑、移除、恢复、质量检查、导出 | 可追溯用例集及 XLSX/CSV 文件 | Step 08 通过且至少选择一个测试点 |

页面数据只能按上述方向前进。用户修改上游已确认内容时，系统必须明确标记受影响的下游草稿为需要重新确认，不得静默保留已经失效的测试点或用例。

## User Stories

1. 作为测试工程师，我希望创建测试设计项目并填写测试对象和软件版本，以便后续需求和用例具有明确上下文。
2. 作为测试工程师，我希望在左侧统一配置模型供应商、Base URL、模型和 API Key，以便不离开主流程完成 AI 准备工作。
3. 作为测试工程师，我希望先测试 API 连接并看到具体失败原因，以便在上传大量资料前发现配置问题。
4. 作为测试工程师，我希望一次上传一份或多份需求文件，以便同时分析 PRD、接口说明和补充规则。
5. 作为测试工程师，我希望看到每个文件的格式、大小、解析状态和诊断信息，以便识别不可读或部分解析的资料。
6. 作为测试工程师，我希望解析失败只影响对应文件，以便其他可读材料仍能继续处理。
7. 作为测试工程师，我希望在结构预览中查看文档标题、章节、表格和来源位置，以便先确认解析结果是否可信。
8. 作为测试工程师，我希望需求分析按合理批次执行并显示当前阶段，以便长文档不会表现为无响应。
9. 作为测试工程师，我希望看到预计剩余时间和已完成数量，以便决定继续等待还是停止。
10. 作为测试工程师，我希望能够停止正在进行的分析或生成，以便错误配置或范围过大时及时控制成本。
11. 作为测试工程师，我希望停止后保留已经完成并校验通过的阶段结果，以便调整范围后继续，而不是全部重来。
12. 作为测试工程师，我希望只在一张按模块分组的需求确认表中工作，以便不需要在需求表和原子需求候选之间重复操作。
13. 作为测试工程师，我希望需求行显示名称、类型、模块、正文摘要、来源和问题标记，以便快速判断其是否应进入测试设计。
14. 作为测试工程师，我希望验收条件显示在对应需求行的展开内容中，以便理解需求而不产生第二张重复表。
15. 作为测试工程师，我希望内部原子拆分和来源引用显示在需求详情中，以便需要时审查追溯关系，但不干扰日常筛选。
16. 作为测试工程师，我希望按模块、类型、问题状态和关键字筛选需求，以便处理大型需求集。
17. 作为测试工程师，我希望对当前筛选结果批量全选或取消，以便快速确定测试范围。
18. 作为测试工程师，我希望未勾选需求明确标记为不进入后续流程，以便生成结果不会包含意外范围。
19. 作为测试工程师，我希望确认需求前看到已选数量、未选数量和阻塞问题，以便理解确认动作的影响。
20. 作为测试工程师，我希望需求确认后自动获得稳定需求 ID，以便测试项、测试点和用例能够持续追踪。
21. 作为测试工程师，我希望需求确认后仍可查看原始来源，但不能静默覆盖确认历史，以便保持可审计性。
22. 作为测试工程师，我希望在“新增建议”页看到歧义、遗漏、冲突、缺少验收条件、异常、边界和风险建议，以便补充需求质量评审。
23. 作为测试工程师，我希望每条建议标明来源事实、分析推导或待确认，以便区分材料内容与 AI 判断。
24. 作为测试工程师，我希望采纳、拒绝、修改或标记建议待外部确认，以便 AI 不能代替人工决定。
25. 作为测试工程师，我希望被采纳为新需求的建议重新进入明确的确认动作，以便补充内容也获得稳定需求 ID。
26. 作为测试工程师，我希望需求冲突只阻塞受影响的需求或模块，以便无关范围可以继续。
27. 作为测试工程师，我希望在“审核”页看到需求模块、测试项、测试点和预计用例之间的层级关系，以便理解生成依据。
28. 作为测试工程师，我希望测试项必须关联一个或多个已确认需求 ID，以便范围不会脱离需求事实。
29. 作为测试工程师，我希望测试点按正常、异常、边界、风险和权限等方向组织，以便获得系统化覆盖。
30. 作为测试工程师，我希望测试点只表达“测什么”，不提前混入操作步骤和具体预期，以便测试设计层次清楚。
31. 作为测试工程师，我希望选择需要生成用例的测试项或测试点，以便控制调用规模和结果数量。
32. 作为测试工程师，我希望系统自动选择适用的场景法、等价类、边界值、判定表、状态迁移、错误推测或风险方法，以便不需要逐个配置算法。
33. 作为测试工程师，我希望测试方法和设计依据默认折叠保存，以便专家可以审查，但普通用户只处理测试范围和用例。
34. 作为测试工程师，我希望生成的每条用例都关联稳定需求 ID、测试项和测试点，以便从用例回溯生成依据。
35. 作为测试工程师，我希望每条用例包含标题、目标、前置条件、测试数据或输入、步骤、逐步预期、整体预期和优先级，以便直接评审和执行。
36. 作为测试工程师，我希望不同边界值或等价类形成独立用例，以便每条用例可以独立编号、确认和执行。
37. 作为测试工程师，我希望 AI 不确定的阈值、文案或行为明确标记为待确认，以便避免把推测当成事实。
38. 作为测试工程师，我希望用例生成失败时看到失败阶段、原因和可执行建议，以便决定重试、缩小范围或使用模板回退。
39. 作为测试工程师，我希望仅对超时、限流和临时连接错误有限重试，以便避免鉴权或格式错误被无意义重复调用。
40. 作为测试工程师，我希望 AI 失败后可以选择模板回退，以便仍能获得基于已确认需求和测试点的基础用例草稿。
41. 作为测试工程师，我希望回退用例有醒目标记，以便不会被误认为模型完成的高质量结果。
42. 作为测试工程师，我希望在测试用例表中搜索、筛选、批量选择、编辑、移除和恢复用例，以便形成最终交付集。
43. 作为测试工程师，我希望质量检查提示孤立测试点、缺失字段、不可验证预期和重复用例，以便在导出前修正。
44. 作为测试工程师，我希望质量指标来自确定性计算，以便覆盖率和数量不会由模型臆测。
45. 作为测试工程师，我希望默认使用平台标准用例表预览，即使自定义模板映射失败也不阻塞评审。
46. 作为测试工程师，我希望导出选中的测试用例为 XLSX，并可选择 CSV，以便交付到现有测试流程。
47. 作为测试工程师，我希望导出的软件版本来自项目上下文，以便不会与需求版本或模型版本混淆。
48. 作为测试工程师，我希望步骤和预期在单元格中连续编号且不插入空行，以便导出文件可直接使用。
49. 作为测试工程师，我希望随时通过快速导航定位当前步骤、阻塞项和下一步动作，以便不在长页面中迷失。
50. 作为测试工程师，我希望后台保留资产来源、AI 运行、Prompt 版本、尝试记录和人工处置，以便需要时审计，但它们不阻塞日常生成。
51. 作为测试工程师，我希望前端步骤与需求分析 Skill 的 Step 00～08 对应，以便界面简化后仍保留完整分析逻辑。
52. 作为测试工程师，我希望能够查看当前 Skill 步骤、输入版本、输出版本和校验状态，以便定位分析失败发生在哪一层。
53. 作为测试工程师，我希望按需导出 Step 00～08 的 Markdown 分析产物，以便与离线 Skill 工作流互通，但不必在日常操作中管理这些文件。
54. 作为测试工程师，我希望模型列表来自当前服务商或明确标记的预设候选，以便不会把不存在或无权限的模型误认为可用。
55. 作为测试工程师，我希望已验证模型在普通刷新后仍可见，而不会重复请求服务商，以便减少等待和调用成本。
56. 作为测试工程师，我希望临时 API Key 默认只保存在当前页面或进程内，以便不会在未授权时持久化敏感凭据。
57. 作为测试工程师，我希望只有勾选“记住临时 API Key”时才保存到本地凭据配置，以便明确控制密钥持久化。
58. 作为测试工程师，我希望连接或调用失败时看到错误阶段、是否可重试和下一步操作，以便自行修正配置。

## Implementation Decisions

- 工作台采用五个一级页签：上传文档、结构预览、新增建议、审核、测试用例。页签按顺序解锁，并显示未开始、进行中、需处理、已确认和失败状态。
- 左侧常驻区域只保留模型服务配置、连接测试、当前流程状态、进度、预计剩余时间、停止按钮和快速导航。项目管理和高级后台入口使用次级导航。
- 资产来源、AI 运行审计、执行任务、执行批次、执行结果、治理指标、变更影响和完整报告继续保留后端能力，但从 MVP 主流程中隐藏或降级到“高级/后台”入口。
- 结构解析与语义分析分离。解析器只产出文档结构、片段、表格、媒体和稳定来源引用；AI 只在可读解析结果上执行语义分析。
- 需求确认表是唯一面向用户的需求选择界面。内部原子需求候选不再作为独立主表；它们作为需求行的追溯详情保存。
- 验收条件属于需求行的附属集合，不作为与需求并列的主操作对象。验收条件可以展开、编辑和标记待确认。
- 用户勾选的是语义需求行。只有已勾选且完成确认的需求可以进入评审建议、测试范围和用例生成。
- 稳定需求 ID 由平台在确认时确定性生成。模型只能返回本次运行内的候选键，不能创建正式稳定 ID。
- 被采纳的新增建议如果改变需求事实，先创建补充需求候选，再由用户确认并分配稳定需求 ID；普通风险或测试建议不反向改写需求事实。
- “新增建议”承载需求质量评审，包括歧义、遗漏、冲突、不可测试、缺少验收条件、依赖未明确、异常或约束缺失，以及分析推导出的边界和风险提醒。
- “审核”承载测试范围确认，不再暴露风险打分、自动化评分和维度树的全部编辑能力。高级风险和自动化信息可以显示在折叠详情中，但不成为生成前的强制表单。
- 统一关系为：需求模块包含已确认需求；测试项关联一个或多个稳定需求 ID；测试点归属于测试项并关联需求或规则；测试用例关联一个测试点、一个测试项和一个或多个稳定需求 ID。页面必须能够沿这条关系正向展开和反向定位。
- 当前领域中的测试范围项作为正式内部对象；主界面可使用更易理解的“测试项”文案。测试点成为测试范围项到用例之间的轻量设计对象。
- 需求分析专用 Skill 是 Step 00～08 工作流的规范来源。平台保留其步骤、编号、来源标签、待确认处理、版本续跑、测试点边界和覆盖自检语义；运行时用结构化阶段契约表达，Markdown 作为兼容导出而不是数据库主模型。
- 用例生成专用 Skill 接收 Step 07 测试点及必要的 Step 02 规则和 Step 08 限制，负责测试方法调度、详细用例、用例编号、去重和质量自检。平台已有用例模型、人工编辑和导出能力负责其后的资产管理。
- 在拆分业务实施 tickets 前，先建立两个仓库范围的项目专用 Agent Skill：`ai-test-design-requirement-analysis` 和 `ai-test-design-case-generation`。它们分别从用户指定的两个外部 Skill 派生，并记录来源与改造边界。
- Skill 派生不是永久原样复制。第一轮必须完成名称和触发描述修改、项目领域术语映射、输入输出契约替换、ID 与优先级统一、通用示例替换、无关文件裁剪及引用检查。
- 需求分析专用 Skill 保留原有 Step 00～08、六维框架、来源标签、待确认规则、测试点层级和确定性自检；将“九个文件”映射为九类结构化阶段产物，并保留兼容 Markdown 渲染器。
- 用例生成专用 Skill 保留测试方法选择、可追溯用例、可验证预期、去重与质量检查；改用平台 P0～P3、稳定需求 ID、测试项和测试点关系，以及平台正式用例模型，删除固定电商规则和按方法输出多份文件的要求。
- 项目专用 Skill、平台领域模型、页面筛选、质量检查和导出统一使用 P0、P1、P2、P3 四级优先级。P3 表示低风险、低频、UI 细节或极端罕见场景；任何可能造成资金、数据、安全或系统可用性损失的场景不得仅因低概率降为 P3。
- Skill 阶段编号与平台稳定 ID 不要求字面相同。`S07-TP-*` 等阶段内编号用于表达分析步骤和来源；平台测试点 ID 用于跨运行、编辑、用例和回归追踪。适配器必须保存二者映射，并保证唯一、稳定、可反查，不能依靠行号或编号邻近推断关系。
- 项目专用用例生成 Skill 的正式输出在原 8 字段基础上新增或明确：测试目标、逐步预期、整体预期、证据要求、用例设计依据、软件版本、稳定需求 ID、测试项 ID 和测试点 ID。逐步预期与操作步骤一一对应；设计依据记录采用的测试方法、代表值、条件组合或风险来源。
- 用例导出模板没有对应列时，证据要求和设计依据可以保留在平台详情或映射到用户确认的扩展列，但不得从内部正式用例模型中丢失。软件版本默认继承项目上下文，并允许用户在导出前确认。
- 原需求分析 Skill 的文档预处理能力由平台解析器承接；其有序内容、媒体清单、来源块 ID 和视觉核对边界必须保留。原 Markdown 校验规则迁移为结构化契约校验，同时继续用于兼容导出的离线校验。
- 两个项目专用 Skill 先通过结构校验，再使用同一组小型合成需求分别做一次正向、信息不足和模型失败场景验证。验证结果用于修正规则后，才开始依据它们拆分和实施业务 tickets。
- 两个工作区外的原始 Skill 不作为生产依赖。仓库内经过适配和验证的两个 Skill 包作为版本化工作流资源随产品发布；后端按当前阶段读取其指令、引用、模板和结构化契约，组装模型请求并执行确定性校验。运行时不得回读工作区外原始目录，也不得动态执行未经登记的任意 Skill 或脚本。
- 高层测试缝只有一个：提交已确认需求、选中测试范围和生成选项，返回统一工作流运行及最终候选用例集。内部阶段不得迫使前端分别理解各模型供应商或 Skill 文件格式。
- AI 运行使用项目自有的阶段协议：排队、解析、分析、校验、等待确认、生成、回退、完成、已停止和失败。每个阶段记录开始时间、完成数量、总数量、错误类型和可恢复点。
- 预计时间使用已完成批次的实际耗时滚动估算；没有足够样本时显示范围或“正在估算”，不能给出虚假精确时间。
- 停止操作在当前不可中断的供应商请求返回后生效，后续批次不得启动。已完成且通过校验的结果保存为草稿。
- 需求分析按文档结构和模块分批，单批输入包含来源目录、稳定片段引用和有限正文。先生成需求候选，再独立生成评审建议；避免一次响应同时承担全部需求、测试项、验收条件、发现和冲突。
- 用例生成按所选测试项或测试点分批，每批只传入必要的已确认需求、验收条件、规则、来源摘要和设计方向。不同批次的用例经确定性 ID、引用和字段校验后合并。
- Prompt 明确区分材料事实、人工确认、分析推导和待确认。输出不得复制无关全文，不得生成来源目录中不存在的引用。
- 每个 AI 阶段使用独立版本化结构契约。响应必须先经过 JSON 提取、字段归一化、Schema 校验、引用存在性、ID 唯一性和跨对象关系校验，成功后才成为可编辑草稿。
- Schema 错误不重复调用同一请求。允许一次本地确定性修复；仍失败时可使用一次专门的结构修复请求，修复请求不得新增业务内容。修复失败后转入人工重试或模板回退。
- 仅超时、限流、连接重置和供应商 5xx 允许自动重试；重试次数和退避有上限。鉴权、参数、内容安全和稳定 Schema 错误不自动重试。
- 模板回退使用同一输入输出契约，根据已确认需求、测试点类型和来源生成最小可编辑用例；回退结果标记来源，不能伪装成真实模型输出。
- 真实模型用例生成必须直接产生候选用例结构；不能只调用模型生成一个通用成功标记，再完全忽略模型输出并使用固定文案构造用例。
- 用例优先级统一为 P0、P1、P2、P3，与当前平台保持一致。Skill 中固定的 P0 比例仅作为提示性诊断，不作为有效性门槛，也不能为了满足比例机械调级。
- 用例标准模型继续支持逐步预期、整体预期、证据要求、设计依据、模板映射、软件版本和稳定追踪。Skill 的 8 字段模板只作为最小兼容视图，不覆盖平台更丰富的正式模型。
- 测试方法属于内部用例设计依据。普通用户默认只看到用例和来源；需要审计时可以展开方法、代表值、组合依据和风险来源。
- 覆盖率由稳定需求 ID、测试项、测试点和用例之间的明确关系计算。AI 可以提出缺口建议，但不能直接给出不可复算的覆盖百分比。
- 模型配置继续只在当前会话或后端环境中使用，API Key 不进入数据库、日志、Prompt 审计、报告或导出物。
- AI 模型接入遵循 `ai-model-integration-skill`：服务商、Endpoint、模型 ID 和 Key 相互隔离；Key 来源优先级固定为临时 Key、用户明确记住的本地 Key、项目默认环境变量。
- 临时 Key 默认只保存在页面内存和当前后端进程；用户明确选择记住后，才写入项目本地凭据配置。现有数据库中的明文会话 Key 不再作为 v0.2.0 的持久化方案，升级时必须清除或迁移为不含 Key 原值的状态记录。
- 模型配置支持 DeepSeek、硅基流动、Kimi、GLM 和自定义 OpenAI 兼容服务。各服务商使用独立环境变量和可覆盖 Endpoint，不得跨服务商复用 Key。
- 提供用户主动触发的模型发现。支持列表接口时读取真实模型 ID；不支持时低成本探测预设候选。预设、已发现、已验证、失败、失效和手动输入模型必须分开展示。
- 只有连接测试成功的模型才能标记为已验证。非敏感验证记录保存服务商、Endpoint、模型 ID、Key 来源、状态和验证时间；Key 或 Endpoint 变化后记录转为失效。
- 模型连接与调用错误使用统一结构，至少包含错误阶段、服务商、模型、错误类型、是否可重试、用户消息、处理动作和脱敏详情。任何 Mock、备用模型或服务商降级都需要用户明确同意。
- 前端只调用本地后端代理进行模型发现、连接测试和正式请求，不向浏览器之外暴露本地默认 Key，也不把仅完成 UI Mock 视为模型接入完成。
- Mock 和真实模型继续明确区分。自动化测试默认使用确定性 Fake/Mock 模型，不消耗真实供应商额度。
- 新规格优先复用现有的需求资料、来源引用、需求确认、稳定需求 ID、设计资产、用例、模型服务适配、AI 运行、模板映射和导出能力；不为接入 Skill 新建平行领域模型。
- 现有已接受的“用户以需求表和用例表为主要工作对象”架构决策继续有效。本规格进一步取消原子需求独立主视图，并收敛测试设计页面。
- v0.2.0 不删除现有后台领域对象和历史记录。界面隐藏或降级的模块继续通过原有存储和 API 保持可访问，后续版本可以重新组合使用。
- 数据库变化优先采用可追加迁移。现有需求版本、需求评审、测试设计和候选用例应能够继续读取；无法映射到新主流程的历史字段保留为高级详情，不进行破坏性清理。
- 已确认需求的稳定 ID 和已存在用例的稳定关系不得因页面重构重新生成。新增测试点对象使用确定性候选键和持久化 ID，避免每次重跑产生无意义重复项。
- 前端通过统一工作流视图组合现有能力，不让五个页签分别持有互相冲突的项目、版本、评审和生成状态。刷新页面后应能从后端恢复当前步骤和可继续动作。
- 保持现有细粒度 API 可供后台和兼容测试使用；为主流程增加一个高层工作流查询模型，聚合当前步骤、阻塞项、进度、可执行动作和关键资产标识。命令操作仍由明确的阶段接口完成，避免单个万能更新接口。
- v0.2.0 的默认入口只展示主流程。高级后台入口必须与当前步骤视觉分离，不能通过错误、未配置状态或待处理数量阻塞五页签流程。

### 分阶段实施计划

1. **阶段 0：Skill 派生与契约基线。** 建立两个仓库专用 Agent Skill，保留需求分析 Step 00～08 和测试点到用例的交接，完成术语、ID、优先级、结构化阶段契约及 Markdown 兼容输出适配；使用合成需求完成基线验证。
2. **阶段 1：模型接入与主流程外壳。** 按 `ai-model-integration-skill` 修正 Key 保存、服务商隔离、模型发现、验证记录、结构化错误和连接测试；建立五页签、左侧模型与进度区、步骤状态和高层工作流查询。
3. **阶段 2：上传到需求确认纵向切片。** 打通模型连接测试、多文件上传、解析、结构预览、单一需求表、验收条件展开、筛选勾选和稳定需求 ID 确认。
4. **阶段 3：评审建议到测试范围纵向切片。** 打通建议生成与处置、补充需求回流、模块—测试项—测试点关系、范围选择和审核确认。
5. **阶段 4：真实用例生成纵向切片。** 让模型按所选测试点返回正式候选用例结构，完成跨对象校验、合并、编辑、移除、恢复和设计依据折叠展示。
6. **阶段 5：稳定性与回退。** 增加分批运行、真实进度、预计时间、停止恢复、错误分类、有限重试、结构修复和模板回退。
7. **阶段 6：质量与导出。** 完成确定性覆盖检查、重复与缺失提示、默认模板预览、XLSX/CSV 导出及端到端验收。
8. **阶段 7：兼容与收尾。** 验证历史数据读取、后台入口、现有治理测试和升级路径，删除仅属于旧首屏组合方式的死代码，不删除仍有后台用途的能力。

每个实施阶段都必须形成可运行、可观察的用户结果。`to-tickets` 应按这些纵向结果拆分 tracer-bullet tickets，而不是分别创建只有数据库、只有 API 或只有页面且无法独立验收的横向任务。

## Testing Decisions

- 最高测试缝是完整应用服务/API 主流程：从已登记需求资料创建当前任务，经过解析、需求分析、选择与确认、建议处置、测试范围确认、候选用例生成，最终导出用例文件。测试验证可观察状态和产物，不绑定内部函数。
- 使用一个确定性模型替身覆盖正常结构化输出、空结果、部分批次失败、超时后成功、限流耗尽、鉴权失败、Schema 错误、引用缺失、输出截断、用户停止和模板回退。
- Skill 映射测试逐步验证 Step 00～08 的输入、输出、编号和依赖关系，并验证 Step 07 测试点能够无损交给用例生成 Skill；测试界面可见行为和结构化阶段契约，不匹配整段 Prompt 文本。
- 模型接入测试验证各服务商配置隔离、Key 来源优先级、主动模型发现、已验证模型缓存、Endpoint 或 Key 变化失效、连接测试状态和结构化错误；测试和 CI 使用替身服务，不读取真实 Key。
- 需求分析契约测试必须验证：每条需求具有有效来源；验收条件只关联存在的需求；未选择需求不进入后续；确认时才产生稳定需求 ID；新增建议不能静默成为需求事实。
- 测试范围契约测试必须验证：每个测试项至少关联一个已确认需求；每个测试点关联存在的测试项；正常、异常、边界、风险和权限方向只在适用时生成；未勾选范围不进入用例生成。
- 用例生成契约测试必须验证：每条用例关联存在的测试点、测试项和稳定需求 ID；必填字段完整；步骤顺序连续；预期可验证；优先级合法；来源引用存在；候选 ID 唯一。
- ID 映射测试验证 Skill 阶段编号与平台稳定 ID 可以采用不同格式，但必须保持一对一或明确的一对多来源映射，并支持从导出用例反查 Step 07 测试点。
- 用例字段测试验证 P0～P3、逐步预期、整体预期、证据要求、设计依据和软件版本在生成、保存、编辑、恢复及导出映射过程中不会丢失。
- 重试测试只观察错误分类、尝试次数、停止条件和最终状态，不依赖具体等待时长。不可重试错误必须只调用一次供应商。
- 停止测试验证后续批次不再启动、已校验草稿得以保留，并且继续运行从明确的恢复点开始。
- 回退测试验证真实模型失败后不会自动伪装成功；只有用户选择或策略允许时创建回退草稿，并在页面、持久化和导出前预览中明确标记。
- 前端组件测试覆盖五页签解锁状态、单一需求表、展开验收条件、筛选勾选、未选择需求隔离、进度与停止、建议处置、范围选择、用例编辑与导出。
- 增加一条浏览器级主流程验收测试，使用小型合成需求包完成上传至导出，确保普通用户不访问高级后台也能完成任务。
- 导出测试验证 XLSX 列顺序、软件版本、步骤与预期换行、选择范围、稳定 ID 追溯和回退标记；CSV 作为备用格式单独验证。
- 质量检查使用确定性规则验证孤立需求、孤立测试点、重复用例、字段缺失、引用失效和不可验证预期。主观内容质量通过有限样例评审，不使用脆弱的全文字符串匹配。
- 验收门槛包括：五页签主流程可独立完成；首屏不展示后台治理模块；需求只在一张表中选择；未勾选需求产生零条后续测试点和用例；真实模型输出实际形成用例内容；暂时性失败可恢复；不可恢复失败可回退；导出文件可直接打开且字段正确。
- 现有需求导入、需求评审、测试设计、用例生成、模型配置和导出相关测试作为先例。旧的后台治理测试继续保留，确保界面降级不等于删除后端能力。

## Acceptance Criteria

### 主流程

- 新用户无需进入高级后台，即可从项目创建完成需求文件上传、解析、确认、评审建议处置、测试范围选择、用例生成和导出。
- 五个页签按状态顺序解锁；刷新页面后当前步骤、选择结果、阻塞项和可继续操作保持一致。
- 左侧区域能够完成模型配置和连接测试，并在 AI 运行时显示阶段、完成数量、总数量、可理解的预计时间和停止操作。
- 模型配置能够区分预设、发现、验证、失败和手动模型；普通刷新不重复发现，用户主动刷新或配置变化后可以重新获取。
- 临时 Key 未勾选记住时不会写入数据库或磁盘；记住时只写入被 Git 忽略的本地凭据配置，API 和页面永不回显原值。

### 需求分析与确认

- 支持当前项目已经声明的 Markdown、文本、JSON、YAML、OpenAPI、DOCX、PDF 和图片输入；无法完整解析时显示文件级诊断，并允许其他材料继续。
- 结构预览只出现一张需求确认表。原子需求、来源引用和验收条件只能作为需求行的展开信息或追溯详情，不再形成第二套并列确认流程。
- 取消勾选的需求不会出现在新增建议的正式分析范围、测试项、测试点、候选用例、覆盖率分母或导出文件中。
- 需求确认后获得稳定需求 ID；重复打开、刷新和继续下游流程时 ID 不变化。
- AI 建议明确区分材料明示、人工确认、分析推导和待确认；被采纳为需求事实的新增建议必须重新确认。
- 界面可以定位需求分析 Skill 的 Step 00～08 状态；Step 07 与 Step 08 的测试点和覆盖关系满足 Skill 校验规则，并可生成兼容 Markdown 分析包。

### 测试范围与用例

- 页面可以从需求模块定位到测试项、测试点和用例，也可以从任一用例反查测试点、测试项和稳定需求 ID。
- 生成范围以用户在审核页的勾选结果为准，未选择测试项或测试点产生零条对应候选用例。
- 真实模型返回的标题、前置条件、输入、步骤和预期实际进入候选用例；不再用通用成功响应触发固定文案生成。
- 每条用例具有合法优先级、连续步骤、可验证预期和有效追溯关系。AI 不确定内容使用待确认标记，不能伪装为需求事实。
- 所有生成、筛选和导出界面统一接受 P0～P3；不再保留只接受 P0～P2 的 Skill 分支逻辑。
- 每条正式用例保存逐步预期、整体预期、证据要求、设计依据和软件版本；即使用户模板未展示全部字段，平台详情和内部记录仍然完整。
- Skill 测试点编号与平台测试点 ID 可以不同，但用户可以从任一用例稳定定位到对应 Step 07 测试点和来源需求。
- 详细用例由用例生成专用 Skill 根据 Step 07 测试点生成；需求分析专用 Skill 不越界生成步骤、数据或具体预期。
- 用户能够编辑、移除、查看已移除项、恢复并按当前选择导出用例；人工修改不覆盖原始候选和审计信息。

### 稳定性与失败处理

- 超时、限流、连接重置和供应商 5xx 按上限重试；鉴权、参数、内容安全和稳定结构错误不会盲目重试。
- 用户停止后不再启动新批次，已完成且校验通过的草稿得到保留；继续运行从明确恢复点开始。
- 模型输出截断、JSON 无效、引用缺失和跨对象关系错误均产生可理解诊断，不会生成看似成功的正式资产。
- 模型不可用时，用户可以选择模板回退生成最小草稿；页面和产物明确显示回退来源。
- Mock、真实模型和模板回退在页面、持久化记录和审计信息中可以区分。

### 导出与兼容

- XLSX 默认导出可以正常打开，并按确认模板输出；步骤和预期连续编号且无多余空行，软件版本来自项目上下文。
- 模板映射失败不阻止平台标准用例预览，并提供可执行的映射诊断或 CSV 备用导出。
- 升级前已存在的需求版本、评审记录、测试设计和候选用例可以读取；隐藏的后台模块不影响主流程，也不会因升级丢失数据。
- 资产来源、AI 运行审计、执行批次、治理指标和变更影响继续通过高级入口或 API 可用，但其未配置或待处理状态不阻止主流程验收。

### 发布完成判定

- 两个仓库专用 Agent Skill 通过结构校验，并在正常、信息不足和模型失败三类合成场景中给出符合项目契约的结果。
- 后端契约测试、前端组件测试、导出测试、历史兼容测试和一条浏览器级端到端主流程全部通过。
- 真实模型至少完成一次受控的小型需求包验收，确认需求与用例均来自结构化模型输出；自动化测试和 CI 不依赖真实 API Key。
- 没有高优先级已知问题会导致未选择需求进入用例、稳定 ID 改变、AI 失败伪装成功、停止操作失效或导出文件不可用。

## Out of Scope

- 不把两个外部 Skill 未经裁剪的副本作为最终项目 Skill，也不在生产运行时加载工作区外 Skill、未经登记的脚本或固定电商示例；生产环境只加载随项目发布并通过校验的专用 Skill 包。
- 不把 00～08 九个 Markdown 文件作为数据库主模型或九个一级页面；保留对应步骤语义、结构化阶段产物和兼容 Markdown 导出。
- 不在 MVP 中实现通用 Skill 市场、Skill 上传、动态安装、任意 Skill 调度或插件权限管理。
- 不在 MVP 首屏展示完整资产来源、AI 运行审计、执行批次、治理指标、变更影响和审计包。
- 不要求用户手工配置八种测试方法、风险权重、自动化适用性因子或复杂维度树。
- 不把产品经理、测试经理和项目经理三角色 AI 评审设为用例导出的必经步骤。
- 不把执行任务发布、外部执行目标、结果导入和复测治理纳入本次主流程验收。
- 不实现账户体系、多人实时协作、真实审批流或权限管理。
- 不用固定 P0 占比、固定用例数量或固定覆盖评分冒充业务质量。
- 不在本规格阶段修改业务代码或创建实施 tickets。

## Further Notes

- 本规格替代现有 rc.2 规格中关于项目工作台信息架构、需求确认交互、测试设计主页面和用例生成实现的部分；资产来源、稳定追踪、模型安全、模板导出和后台治理的既有约束继续有效。
- 两个外部 Skill 是 v0.2.0 测试工作流的上游来源，仓库内适配后的两个专用 Skill 包是产品实际运行的版本化工作流资源。后端工作流适配器加载对应阶段资源并调用所选模型，前端只负责可视化和人工操作；浏览器不直接解释 `SKILL.md`。
- Skill 适配是业务 tickets 之前的准备阶段，但不要求在此时把所有 Prompt 调到最终状态。先完成领域契约和基础样例，主流程实现后再用真实运行失败持续收窄规则。
- 进入实施任务拆分时，第一组 tickets 处理两个项目专用 Skill 的派生、裁剪和基线验证；后续 tickets 按可运行的纵向切片组织，优先实现上传到导出的最短主路径，再补进度恢复、真实模型稳定性和高级后台入口。
- 本文是 v0.2.0 的单一开发规格。旧的 rc.2 规格保留为历史基线；两者冲突时，v0.2.0 在主流程、页面信息架构、Skill 适配和 AI 生成方式上的决定优先。
- v0.2.0 完成后再决定是否把仓库专用 Agent Skill 打包为可安装 Plugin，或把执行与治理能力重新提升为用户可见主流程。

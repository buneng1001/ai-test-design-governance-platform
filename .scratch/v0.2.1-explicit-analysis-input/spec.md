# v0.2.1 需求规格：显式选择需求分析输入来源

Status: ready-for-agent

## Problem Statement

当前 v0.2.0 在需求分析页同时提供“AI 阅读并整理资料（先确认范围）”“确认并执行：AI 阅读并整理资料”“查看调用范围”和“确认并开始需求分析”等操作。调用前预检、真实模型调用和需求分析输入来源使用了相近的名称，测试工程师难以判断哪个按钮只是本地准备、哪个按钮会调用 AI，以及需求分析最终使用原始解析资料还是 AI 整理结果。

“AI 阅读并整理资料”原本用于在生成需求分析表之前，先让模型提取摘要、关键事实、约束和待确认项。但对于单份、结构清晰且长度可控的需求资料，直接把解析正文与需求分析 Prompt 发送给指定模型即可完成任务。强制增加中间整理会产生额外调用、等待时间、Token 消耗和失败点，因此不应成为默认或隐式前置步骤。

当前系统还会在存在同一资料版本的成功整理结果时自动使用它，用户不能明确选择绕过整理结果。这种隐藏选择使调用前展示和实际模型输入不够可预期。

## Solution

v0.2.1 将“直接使用原始解析资料”设为默认需求分析路径，并把“先让 AI 阅读并整理资料”保留为可选增强能力。

资料整理区域的调用前按钮改为“查看整理范围”。该按钮只展示资料数量、来源片段、模型上下文块、预计调用次数、Token、模型和超时策略，不调用 AI。确认按钮明确命名为“发送给 AI 并开始整理”，只有点击该按钮才发生真实模型调用。

需求分析区域提供两个含义明确的入口按钮：

1. `使用原始解析资料生成需求表`
2. `使用 AI 整理结果生成需求表`

两个入口共用既有的模型调用、结构化输出校验、需求表保存和结果展示能力，但必须把输入来源作为显式运行参数保存。系统不得根据是否存在整理结果而在后台自动切换输入来源。

“使用 AI 整理结果生成需求表”仅在当前需求版本存在成功且可用的资料整理结果时可用。整理失败、未完成、为空或属于旧需求版本时，该入口不可执行，并应直接说明原因；不得静默退回原始解析资料。

端到端验收缝为：**上传并解析一份资料，分别选择原始解析资料和 AI 整理结果发起需求分析，确认调用前展示、实际模型输入、运行证据和最终需求表始终使用用户明确选择的同一种来源。**

## User Stories

1. 作为测试工程师，我希望默认直接使用上传资料的解析正文生成需求表，以便减少不必要的模型调用和等待。
2. 作为测试工程师，我希望资料整理是可选功能，以便只在多文档、长文档或内容混乱时使用。
3. 作为测试工程师，我希望“查看整理范围”只展示将发送的资料和预算，以便知道该操作不会调用 AI。
4. 作为测试工程师，我希望只有点击“发送给 AI 并开始整理”才调用模型，以便准确控制 Token 消耗。
5. 作为测试工程师，我希望通过两个独立按钮选择原始解析资料或 AI 整理结果，以便系统不会替我暗中决定输入来源。
6. 作为测试工程师，我希望调用前确认区域明确显示本次分析依据，以便在发送前发现选择错误。
7. 作为测试工程师，我希望正式运行严格使用调用前确认的输入来源，以便预检内容与实际请求一致。
8. 作为测试工程师，我希望没有成功整理结果时不能点击“使用 AI 整理结果生成需求表”，以便避免误以为失败或不完整的结果已被使用。
9. 作为测试工程师，我希望整理结果必须与当前需求版本一致，以便旧版本资料不会进入新版本需求分析。
10. 作为测试工程师，我希望需求分析运行记录保存输入来源和整理运行编号，以便事后核对需求表的依据。
11. 作为测试工程师，我希望相同资料、模型、Prompt 和输入来源不变时可以复用结果，以便避免重复消耗 Token。
12. 作为测试工程师，我希望切换输入来源后不能复用另一来源的结果，以便原始资料分析和整理结果分析保持独立。
13. 作为测试工程师，我希望失败的资料整理检查点可以恢复，以便已经完成的模型工作不被浪费。
14. 作为测试工程师，我希望本地解析、调用前预检和 AI 语义整理使用不同术语，以便理解每一步由谁完成。
15. 作为测试工程师，我希望需求分析完成后仍以统一需求表展示结果，以便输入来源差异不改变后续新增建议、审核和测试用例流程。

## Implementation Decisions

- 版本号定为 `v0.2.1`，作为 `v0.2.0` 需求分析交互和输入来源控制的兼容性修订。
- “原始解析资料”是本地解析器从当前需求版本文件中提取、按来源保留引用并整理成模型上下文的正文；它不是 AI 总结结果。
- “AI 整理结果”是针对当前需求版本成功完成的资料理解运行产物，包含摘要、关键事实、约束、待确认项和原始来源引用。
- 需求分析输入来源采用显式枚举 `raw` 或 `understanding`。调用前预检和正式运行必须接收并保存同一个值。
- `raw` 始终使用当前需求版本的原始解析资料，即使存在成功的 AI 整理结果也不得自动替换。
- `understanding` 必须绑定当前需求版本的一次成功资料整理运行；不存在可用结果时返回可理解的业务错误，不做隐藏回退。
- 输入指纹必须包含输入来源；选择 `understanding` 时还必须包含资料整理运行 ID。不同来源不得互相复用需求分析结果。
- 需求分析运行证据至少显示“分析依据：原始解析资料”或“分析依据：AI 整理结果”，选择后者时显示整理运行 ID 和对应需求版本。
- `查看整理范围` 只执行本地预检。页面用“尚未发送”明确标识，不生成资料整理结果。
- `发送给 AI 并开始整理` 才创建真实资料整理运行。模型成功返回并通过结构校验后，结果才能被标记为可用于需求分析。
- 需求分析页使用两个入口按钮呈现输入来源，不再通过后台自动判断。两个按钮进入同一套调用确认与运行组件。
- 为降低页面按钮数量，Token、调用次数和超时信息收纳在调用确认区域；浏览、展开或取消确认均不得调用模型。
- 模型运行方式继续保持“真实模型（直接调用）”“真实模型（Skill 工作流）”和“本地模式”，它与输入来源是两个不同概念。
- 模型请求仍通过文本消息发送提取后的正文和版本化 Prompt，不把本地文件路径或二进制文件直接交给兼容 Chat Completions 的提供方。
- 单份且长度可控的资料优先采用较少请求；只有达到输入、输出或可靠性边界时才分批。是否分批属于运行策略，不应改变用户选择的输入来源。
- 实施本规格前需修复旧数据库中活动结果表不允许空运行 ID 的兼容问题，确保资料整理完成后能够安全激活结果，并能从既有检查点恢复。
- 新版上线不自动删除已有资料整理运行；历史结果继续作为审计记录保留。

## Testing Decisions

- 以需求分析 HTTP 预检与正式运行组成的集成测试作为主要验收缝，验证用户选择的输入来源贯穿预检、模型请求、运行记录和结果保存。
- 前端测试验证两个输入来源按钮均可见，默认突出原始解析资料入口；没有成功整理结果时，AI 整理结果入口不可执行并显示原因。
- 原始资料路径测试验证存在成功整理结果时仍只向模型发送原始解析正文，运行证据标记为原始解析资料。
- AI 整理路径测试验证只发送当前版本的指定整理结果，并保留其原始来源引用。
- 一致性测试验证预检选择与正式运行选择不一致时拒绝执行，切换来源会清除旧确认信息。
- 版本测试验证上传新需求版本后，旧整理结果不可用于新版本需求分析。
- 失败测试验证整理失败、停止、结果为空或结构校验失败时，AI 整理结果入口不可用且不会回退至原始资料。
- 复用测试验证相同输入来源可复用完全一致的成功结果，而 `raw` 与 `understanding` 永不交叉复用。
- 恢复测试验证完成全部模型分块但在最终保存阶段失败的资料整理，可从检查点恢复且不重复调用模型。
- 数据库迁移测试从旧版活动结果表结构升级，验证已有项目和运行保留，并能将下游活动结果安全置空。
- 持续集成使用确定性模型替身，不调用真实供应商；真实模型只用于人工验收响应时间和结构化输出兼容性。

## Out of Scope

- 本规格不删除 AI 资料整理能力。
- 本规格不要求所有需求资料一次性发送；分批策略可根据模型限制独立优化。
- 本规格不增加新的文件上传协议、供应商文件 API、OCR 或视觉模型能力。
- 本规格不修改需求分析表字段、新增建议、审核或测试用例的数据结构。
- 本次仅记录下一版本规格，不在当前工作中修改界面、接口、数据库或模型调用行为。

## Further Notes

- 当前 v0.2.0 的“AI 阅读并整理资料（先确认范围）”实际上是本地调用前预检，不会调用 AI；这一命名是本规格需要纠正的主要认知问题。
- 对单份且约数千 Token 的结构化需求资料，直接需求分析通常是更简单的默认路径。资料整理主要面向多文档、长文档、结构混乱或需要跨后续阶段复用统一资料理解的场景。
- 用户在 v0.2.0 中看到资料整理失败后仍能查看需求分析范围，是因为需求分析预检可以独立读取上传资料的原始解析正文；失败的整理运行不会成为可用输入。
- 本规格已记录为下一版本候选，当前版本继续保持现状，待用户决定开始 `v0.2.1` 实施后再拆分任务。

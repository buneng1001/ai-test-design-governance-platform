# 16 — 完成 V1→V2 需求变更和回归治理

**What to build:** 测试工程师导入 V2 需求版本后，可确认原子需求的延续和变化，查看这些变化沿追踪链造成的影响，
治理受影响用例状态，并从确定性候选和 AI 补充建议中确认回归选择。

**Blocked by:** 06 — 完成原子需求、需求评审与需求确认；11 — 治理用例身份、状态和单独下载；
15 — 建立质量问题、缺陷模式和五类覆盖指标。

**Status:** ready-for-agent

- [ ] V2 作为新的不可覆盖需求版本导入，V1 需求、设计、用例和执行结果仍可复现。
- [ ] AI 提出新增、修改、删除、拆分、合并和疑似延续的需求变更，并保留两个版本的来源引用。
- [ ] 测试工程师确认需求变更后，变更影响才可进入正式治理流程。
- [ ] 变更影响沿已确认追踪关系列出受影响的测试范围、风险、测试用例、测试任务和回归候选。
- [ ] 受影响用例进入待影响确认，不被 AI 自动关闭、废弃、替代、修订或纳入执行。
- [ ] 测试工程师可保留、修订、关闭、废弃或替代用例，并分别决定当前测试参与状态。
- [ ] 确定性回归候选包含需求变更、高风险、历史失败或异常、结果冲突、未关闭质量问题、缺陷模式、相邻状态和长期未执行用例。
- [ ] AI 只能附理由补充回归候选，不能移除确定性候选或自动形成回归选择。
- [ ] 测试工程师确认纳入或排除及必要理由后形成回归选择。
- [ ] API 与前端测试覆盖一个完整 V1→V2 场景、历史不变性、影响路径、状态治理和回归确认。

# AI 运行多实例与接管设计说明

## 适用范围

Ticket 09 的实现以单实例部署为前提：服务重启代表旧进程已经退出，因此启动恢复可以释放未完成批次并从数据库检查点继续。它不等同于支持多个后端实例同时处理同一运行。

当系统引入容器副本、滚动发布、任务队列 worker 或灾备切换时，应先完成本文设计，再允许多个实例执行 AI 运行。

## 主要风险

- 新实例直接清理活动批次，旧实例可能仍在等待或调用模型，导致同一批模型被重复调用。
- 停止请求只到达一个实例，其他实例仍可能启动下一批或重试。
- 旧 worker 在新 worker 接管后晚返回，可能写入过期检查点或影响最终资产。
- 网络分区会让两个实例都误以为自己仍拥有运行。

## 推荐状态与数据

在 `ai_run_controls` 或独立的 `ai_run_leases` 表保存以下字段：

- `owner_id`：实例或 worker 的随机、可追踪标识。
- `lease_id`：每次领取批次生成的 fencing token。
- `lease_expires_at`：租约到期时间。
- `heartbeat_at`：最近一次续租时间。
- `active_batch_number`：当前被领取的批次。
- `stop_requested_at` 与 `stop_requested_by`：协作式停止审计信息。

所有“保存检查点、创建最终资产、标记完成”的 SQL 都必须带 `lease_id` 条件；不匹配时拒绝写入。这样旧 worker 即使晚返回，也不能覆盖新 owner 的结果。

## 领取、续租与接管

1. worker 在一个数据库事务内原子领取下一批，写入 owner、lease token 和到期时间。
2. 调用模型期间定期续租；无法续租时立即停止后续写入。
3. 其他 worker 只能在租约到期后接管，接管时生成新的 fencing token。
4. 运行停止时不再领取新批次或重试；已领取调用应尽快返回，或等租约到期后由接管方处理。
5. 不要由新实例“强杀”旧实例。强制终止需要明确的管理权限、实例发现和审计，并应作为独立运维能力实现。

## 发布与运维建议

- 滚动发布先停止领取新批次，再等待在途批次完成或租约到期，最后下线旧实例。
- 为运行、租约超时、接管次数和重复领取记录指标与告警。
- 管理界面提供“请求停止”“查看 owner/租约”“在租约到期后接管”；不要提供无审计的立即接管。
- 对模型服务设置调用超时，避免永久占用租约；超时后遵循既有受限重试策略。

## 验收建议

- 两个实例同时推进同一运行，仅一个实例调用模型。
- owner 崩溃或停止续租后，另一实例只能在到期后接管。
- 旧 owner 在接管后返回时，检查点和最终资产写入被 fencing token 拒绝。
- 停止在 owner 之间传播后，不产生新批次和新 retry。
- 滚动发布、网络分区恢复和数据库故障恢复均保留可审计检查点。
